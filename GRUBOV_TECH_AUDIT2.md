| **Логика диалога** | Общая для всех мессенджеров | `conversation.js` (403) |
| **Адаптеры мессенджеров** | Telegram / MAX | `bot.js` (102), `max-bot.js` (294) |

| **БД** | PostgreSQL, 10 таблиц | схема в `schema.js` |

### Фоновые задачи

Планировщика как такового нет — три `setInterval` внутри процесса:

1. `escalation.js` — каждые 30 минут повышает приоритет заявок, простоявших дольше 12 часов, и уведомляет водителя. **Работает и проверено в бою:** в логах 18 августа видно «Повышен приоритет у заявок: 6», затем «: 1».
2. `api.js` — раз в сутки чистит просроченные сессии.
3. `api.js` — раз в 30 минут чистит счётчики попыток входа.

Очередей, брокеров, внешнего cron нет. При перезапуске контейнера таймеры стартуют заново — потерь нет, поскольку задачи идемпотентны.

### Потоки данных

**Диспетчер:**
```
браузер (index.html) → fetch с Bearer-токеном
  → Express /api/* (api.js)
  → auth: сессия → аккаунт → company_id + role
  → SQL прямо из обработчика роута
  → PostgreSQL
  ↳ побочно: notifier → канал заявки (Telegram или MAX) → водитель
```

**Водитель в мессенджере:**
```
Telegram/MAX → адаптер (bot.js / max-bot.js)
  → conversation.handle() — общая логика, не знает про мессенджер
  → db.js → PostgreSQL
  ↳ ответы возвращаются массивом; адаптер переводит их в формат своего API
```

**Водитель в кабинете:**
```
ссылка из бота с токеном после # → driver.html
  → /api/driver/* (driver.js), авторизация по driver_sessions
  → только свои данные: своя машина, свои заявки
```

**Администратор сервиса:**
```
admin.html → /api/admin/* (admin.js)
  → отдельные таблицы admins / admin_sessions
  → доступ ко всем компаниям
```

### Авторизация: три независимых контура

| Контур | Таблицы | Срок | Где |
|---|---|---|---|
| Сотрудники компаний | `accounts`, `sessions` | 30 дней | `api.js` |
| Водители (кабинет) | `driver_sessions` | 90 дней | `driver.js` |
| Администраторы сервиса | `admins`, `admin_sessions` | 7 дней | `admin.js` |

Разделение верное: компрометация одного контура не даёт доступа к другим. Пароли везде — `scrypt` со случайной солью и сравнением через `timingSafeEqual`.

### Deployment

Push в GitHub → Railway собирает (nixpacks) → выкатывает. `railway.toml`: healthcheck `/health`, рестарт при падении до 5 раз. Миграции применяются при старте (`initSchema`), все операции идемпотентны. CI-проверок нет, staging нет, бэкапы не подтверждены.

## 2. Карта модулей

### Core

**`conversation.js` (403) — логика диалога с водителем.**
Сценарии: привязка аккаунта (по идентификатору мессенджера, нику, подтверждённому телефону, e-mail), создание заявки, профиль, кабинет, ответ на комментарий.
Зависит от: `db`, `ticket-types`, `driver` (ленивый require внутри функции).
От него зависят: `bot.js`, `max-bot.js`.
**Автономность высокая.** Не знает ни про Telegraf, ни про HTTP: на входе обезличенное событие, на выходе массив ответов. Это лучший модуль в проекте с точки зрения границ.

**`api.js` (838) — основной API.** ⚠️ **God module**
Внутри: хеширование паролей, защита от подбора, сессии, middleware авторизации, CRUD четырёх сущностей, приглашения, импорт, рассылка, синхронизация связи водитель↔машина, справочник каналов.
Зависит от: `db`, `ticket-types`, `notifier`, `import`, `activity`, `channels`, `settings`.
**Растёт быстрее всех:** 597 → 838 строк за двое суток (+40 %). Пять разных ответственностей в одном файле.

### Infrastructure

**`db.js` (219)** — пул соединений плюс запросы для ботов. Особенность прежняя: API работает с БД напрямую через `db.query`, минуя эти функции. Два стиля доступа к данным сосуществуют.

**`schema.js` (336)** — создание таблиц, идемпотентные `ADD COLUMN`, индексы, триггер. Здесь же — разовое выравнивание связей водитель↔машина при старте (сработало: «Восстановлено связей: 1»).

**`bot-manager.js` (216)** — композиционный корень: схема, боты, роутеры, CORS, эскалация.

### Feature modules

**`settings.js` (284)** — реквизиты компании, профиль, пароль, команда, уведомления. **Единственный модуль, где применяются права** (`requirePermission` — 10 вызовов).

**`admin.js` (549)** — админка сервиса: компании, аккаунты, сброс паролей, блокировка, журнал, управление данными компаний.

**`driver.js` (255)** — кабинет водителя: свои данные, пробег, заявки, комментарии.

**`import.js` (374)** — разбор строк из Excel, приведение типов, поиск дублей, отчёт по строкам.

### Adapters / Integrations

**`bot.js` (102)** и **`max-bot.js` (294)** — адаптеры мессенджеров. `max-bot.js` крупнее из-за собственного HTTP-клиента с сертификатами Минцифры, long polling и проверки подписи контакта.

**`notifier.js` (142)** — отправка через реестр отправителей. Знает про каналы и настройки, не знает про HTTP.

### Shared / правила

`channels.js` (46), `roles.js` (52), `ticket-types.js` (23), `notifications.js` (93), `activity.js` (84), `escalation.js` (52). Все маленькие, с одной ответственностью. Это здоровая часть системы.

### God modules

**`index.html` (3 872)** — весь интерфейс диспетчера: стили, разметка, состояние, сеть, рендер восьми разделов, все модальные окна, drag&drop, импорт, рассылка, настройки. Вырос на 40 % за двое суток.

**`api.js` (838)** — описан выше.

## 3. Архитектура

### Что стало заметно лучше

**Логика бота вынесена из транспорта.** До этого добавление MAX означало бы копию всех сценариев. Сейчас `conversation.js` не знает про мессенджеры, а адаптеры переводят его ответы в свой формат. Это устранило самый дорогой вид дублирования — копирование бизнес-правил между слоями.

**Появились справочники вместо разбросанных констант.** `channels.js` описывает каналы, `roles.js` — роли и права, `ticket-types.js` — типы заявок, `notifications.js` — события уведомлений. Раньше статусы и типы были продублированы в трёх файлах.

**Заявка помнит канал происхождения** (`tickets.channel`), и обратная связь уходит туда же. Это не «если MAX, то так», а общее правило с фоллбэком — новый мессенджер подхватится сам.

**Циклических зависимостей нет.** Граф — дерево, направленное к `bot-manager.js`. Единственный обратный вызов — `require('./driver')` внутри функции `showCabinet` в `conversation.js`, сделан лениво именно чтобы не образовался цикл.

### Что осталось проблемой

**Доменного слоя по-прежнему нет.** Бизнес-правила живут в трёх местах: обработчики роутов (`api.js`), сценарии бота (`conversation.js`), браузер (`index.html`). Пример: «заявка застоялась» вычисляется дважды — на сервере в `escalation.js` (SQL по `updated_at`) и в браузере в `staleHours()` (по массиву `history` и `comments`). Правила похожи, но не идентичны: сервер смотрит на `updated_at`, клиент — на времена в JSONB. Расхождение уже возможно.

**Прямой SQL в роутах.** В `api.js` и `admin.js` запросы написаны в обработчиках. Смена хранилища или добавление кэша потребует правки каждого обработчика.

**Глобальное изменяемое состояние на фронте.** `USERS`, `VEHICLES`, `CONTRACTORS`, `tickets`, `state`, `settingsData`, `broadcastSelected`, `draggedTicketId` — переопределяются из разных функций одного файла на 3 872 строки.

**Скрытые зависимости, которые стоит знать новому разработчику:**

1. `notifier.setBot()` / `setMaxBot()` — если забыть вызвать, уведомления молча не отправляются.
2. Формат `comments` и `history` в JSONB (`author`, `text`, `time`, `internal`, `fromDriver`) нигде не описан, поддерживается соглашением между `api.js`, `conversation.js`, `driver.js` и `index.html`.
3. `DEFAULT_API` прошит в трёх HTML-файлах отдельно. При смене домена сервера нужно поправить все три.
4. Токен приглашения и токен кабинета передаются после `#` — это осознанное решение (не попадают в логи), но неочевидное.

| Этап | Оценка | Комментарий |
|---|---|---|
| Найти место ошибки | **Хорошо** | Логи с префиксами `[api]`, `[bot]`, `[max]`, `[schema]`, `[escalation]`. Появился журнал действий — видно, кто что менял |
| Воспроизвести | **Тяжело** | Staging нет, локальный запуск не описан, нужен свой Postgres и отдельный тестовый бот |
| Понять контекст | **Средне** | Код читаемый, комментарии объясняют «почему». Но README нет, а объём вырос вдвое |
| Исправить | **Легко** | Модули небольшие, зависимости прозрачные |
| Убедиться, что не сломал | **Очень тяжело** | **Тестов по-прежнему ноль** |
| Выкатить | **Легко** | `git push` → Railway |

### Наблюдаемость

**Есть:** структурированные логи, healthcheck со статусом обоих ботов, `bot.catch()` в Telegraf, автоперезапуск polling, журнал действий в БД (`activity_log`) с IP и автором.

**Нет:** идентификаторов запросов, уровней логирования, алертов, метрик, staging.

### Где баг будет сложно локализовать

1. **Уведомление не дошло.** Теперь причин стало больше: бот не запущен, у водителя нет идентификатора канала, событие отключено в настройках компании, попало в тихие часы, канал заявки указывает на мессенджер, где водителя нет. Часть этих веток возвращает `0` молча — в логах не будет ничего.
2. **Расхождение «застоявшихся» заявок.** Клиент считает по одним данным, сервер по другим — карточка может быть красной, а приоритет не повышен, или наоборот.
3. **Импорт «съел» данные.** В `import.js` при обновлении пустые ячейки не затирают значения, а в обычном PATCH — затирают. Разное поведение для одной и той же сущности; пользователь легко перепутает.

## 5. Изменяемость: мысленные тесты

### A. Новое поле у заявки
Менять: `schema.js`, `api.js` (INSERT + UPDATE), `index.html` (форма и рендер), возможно `driver.js`. **3 уровня, риск низкий.**

### B. Новая роль с правами
Менять: `roles.js` (одна запись), затем — **расставить `requirePermission` по всем эндпоинтам, где их сейчас нет**. Это не столько добавление роли, сколько доделка механизма. **4 уровня, риск высокий.**

### C. Новый статус заявки
Менять: `notifier.STATUS_LABELS`, `conversation.js` (иконки), `escalation.js` (список исключений `NOT IN ('DONE','CANCELLED')` — в двух местах), `index.html` (колонки, кнопки, фильтры, подписи, drag&drop). **Дублирование сохранилось:** статусы не вынесены в справочник, в отличие от типов заявок и каналов. **Риск средний, шанс забыть место — высокий.**

### D. Новая интеграция (ещё мессенджер)
Менять: запись в `channels.js`, регистрация отправителя в `notifier`, новый адаптер по образцу `bot.js`. **2 уровня, риск низкий.** Это самое дешёвое изменение — и именно его архитектура готовила.

### E. Изменить бизнес-правило
Пример: «эскалировать через 6 часов вместо 12». Менять `ESCALATE_AFTER_HOURS` — и не забыть `STALE_HOURS` в `index.html`, где порог прошит числом 12. **Дублирование константы между сервером и клиентом.**

### F. Новый раздел в CRM
Менять только `index.html`: `setPage`, функция рендера, пункт меню, `refreshCurrentPage`. **1 уровень, но файл растёт** — восьмой раздел добавлен, каждый следующий дороже предыдущего.

### G. Заменить БД
Менять `db.js` и **каждый обработчик** в `api.js`, `admin.js`, `settings.js`, `driver.js`. **Риск очень высокий.**

### H. Заменить мессенджер
Адаптер плюс поля в схеме. Архитектура готова — **риск низкий**, что доказано добавлением MAX за один заход.

**Вывод:** система отлично принимает новые интеграции и поля, средне — новые статусы и экраны, плохо — изменения в правах и смену хранилища.

## 6. База данных

### Модель

10 таблиц: `companies`, `accounts`, `sessions`, `admins`, `admin_sessions`, `driver_sessions`, `users`, `vehicles`, `contractors`, `tickets`, `activity_log`. Модель соответствует предметной области, переусложнения нет.

### Сделано правильно

- Внешние ключи с осмысленными `ON DELETE`: компания уносит свои данные каскадом, водитель — нет (`SET NULL`).
- Индексы покрывают реальные запросы, включая составной `(company_id, created_at DESC)` и частичный `WHERE max_id IS NOT NULL`.
- Уникальные индексы на `LOWER(email)` — регистронезависимость сделана правильно.
- `updated_at` через триггер.
- Журнал действий с индексами по компании, аккаунту и дате.

### Проблемы

**1. Транзакций по-прежнему ноль.** Поиск по всей кодовой базе: единственное совпадение `BEGIN` — внутри plpgsql-функции триггера. Наиболее опасное место — `syncAssignment()` в `api.js`: четыре последовательных UPDATE, меняющих связи с двух сторон. Если процесс упадёт между ними, связь останется наполовину обновлённой — ровно та ошибка, которую только что чинили. Второе место — `PATCH /tickets/:id`: чтение и запись раздельными запросами, параллельные комментарии могут потеряться.

**2. Миграции необратимы и не версионированы.** `schema.js` умеет только добавлять. Узнать версию схемы на проде нельзя, откатить изменение — тоже. При 10 таблицах и одном разработчике терпимо; при двух ветках начнутся расхождения.

**3. Статусы и роли — свободный текст без `CHECK`.** `status`, `priority`, `type_key`, `channel`, `role`, `payment_type` — обычные `TEXT`. Опечатка в коде создаст запись, которая не отобразится ни в одной колонке, и БД это молча примет.

**4. Двойная связь водитель↔машина сохранена.** `users.assigned_vehicle` и `vehicles.assigned_user_id` — два источника правды. Сейчас они синхронизируются кодом (`syncAssignment` в API, `syncAssignments` в импорте, разовое выравнивание в `schema.js`) — это три отдельных механизма для поддержания того, что могло бы быть одним полем. Работает, но каждая новая точка записи обязана помнить про синхронизацию.

**5. `tickets` — центральная таблица.** Ссылается на компанию, машину, двух пользователей, подрядчика; несёт `channel`, `comments`, `history` в JSONB. Любое изменение её структуры задевает CRM, оба бота, кабинет и уведомления.

**6. Мягкого удаления нет.** Удаление водителя или машины физическое, история теряется.

**7. `notifications` и `specializations` в JSONB.** Для текущих объёмов удобно; минус — нет валидации на уровне БД.

## 7. API

### Структура

Четыре роутера под `/api`: основной, `/settings`, `/driver`, `/admin`. Ресурсы во множественном числе, глаголы корректные. Именование единообразное.

### Хорошо

- Все запросы параметризованные, **SQL-инъекций нет**. Динамическая сборка `SET` идёт по фиксированным белым спискам полей.
- `/bootstrap` — одна загрузка вместо пяти запросов, с ограничением 400 последних заявок.
- Ошибки в едином формате `{ error }`, сообщения на русском и понятны конечному пользователю.
- Изоляция компаний последовательная: проверено — во всех обработчиках `api.js` и `settings.js` присутствует `company_id = $N`.

### Плохо

**1. Права проверяются в одном модуле из четырёх.** `requirePermission` встречается только в `settings.js`. В `api.js` — CRUD водителей, машин, заявок, подрядчиков, импорт, рассылка — проверки роли нет вообще. Роль `viewer`, заявленная как «только просмотр», может удалить водителя, машину и заявку. Подробнее в разделе 9.

**2. Валидация входных данных почти отсутствует.** Проверяется только наличие обязательных полей. Не проверяются: формат почты, длины строк, диапазоны чисел, корректность дат, принадлежность связанных сущностей той же компании (например, `vehicleId` в заявке).

**3. Внутренняя модель торчит наружу.** Ответы — это `rows[0]`, то есть строки таблиц. DTO нет. Переименование колонки ломает фронтенд немедленно.

**4. Версионирования нет.** Пока клиенты выкатываются вместе с сервером — терпимо.

**5. `err.message` из PostgreSQL уходит клиенту** в нескольких местах `api.js` и `admin.js`. Это подсказывает атакующему структуру БД. Severity Low, чинится за 15 минут.

### Можно ли изменить внутреннюю модель, не сломав фронтенд?

**Нет.** Слоя преобразования между таблицами и клиентом нет; частично сглажено функциями `fromServerTicket` / `fromServerDriver` на фронте, но это заплатка, а не контракт.

## 8. Frontend

### Факты

- `index.html` — 3 872 строки, **35 мест с `innerHTML`**, ни сборки, ни модулей.
- `admin.html` (785), `driver.html` (446), `invite.html` (150) — отдельные страницы, в них **есть** полноценная функция экранирования `esc()`.
- В `index.html` функция с именем `esc` объявлена локально внутри `openContractorModal` и экранирует **только кавычки** — для атрибутов, но не для HTML-содержимого.

### Что хорошо

Единая точка сетевых запросов `api()` с обработкой 401. Индикаторы загрузки и всплывающие уведомления. Drag&drop сделан аккуратно: оптимистичное обновление с откатом при ошибке сервера. Три отдельных интерфейса (диспетчер, водитель, админ) — правильное разделение по ролям и устройствам.

### Что создаёт риск

**1. XSS.** Данные вставляются в разметку без экранирования: имена, названия, заголовки заявок и **тексты комментариев**. Разбор — в разделе 9. Это тот же риск, что и в прошлом аудите, и он **не закрыт**, хотя в трёх новых файлах экранирование сделано правильно.

**2. Изменение общих функций ломает несколько экранов.** `refreshCurrentPage()` завязана на `state.page` и вызывается отовсюду. `saveVModal()` — одна функция на три типа карточек с ветвлением по `vModalContext.type`. `renderDriverConnections()` используется двумя разделами.

**3. Дублирование правил с сервером.** `STALE_HOURS = 12`, названия статусов, приоритетов, ролей, каналов — всё продублировано в браузере отдельными объектами.

**4. Формы без валидации.** Даты, телефоны, числа принимаются как есть и уходят на сервер, где тоже не проверяются.

**5. Доступность не рассматривалась.** Для внутреннего инструмента приемлемо.

- **Пароли** — `scrypt` со случайной солью, `timingSafeEqual`. Три контура (сотрудники, водители, админы) с разными сроками жизни сессий.
- **SQL-инъекции** — исключены параметризацией.
- **Изоляция компаний** — последовательная, проверена по всем модулям.
- **CORS** — белый список доменов с `Vary: Origin`. Закрыто по рекомендации прошлого аудита.
- **Подбор пароля** — 8 попыток по IP и почте на 15 минут в CRM, 5 попыток в админке. Закрыто.
- **Сессии** — ограниченный срок с продлением, автоочистка. Закрыто.
- **Подтверждение номера в MAX** — контакт проверяется по HMAC от токена бота. Пересланная чужая визитка не пройдёт. Сделано аккуратнее, чем требовалось.

- **Секретов в репозитории нет.** Сертификаты Минцифры в `certs/` — публичные корневые, это нормально.

Две правки закрывают оба верхних риска и занимают примерно полдня:

1. Одна функция экранирования и её применение ко всем подстановкам в `index.html` (в трёх других файлах она уже есть — можно скопировать).
2. Расстановка `requirePermission` в `api.js`: на удаление — право `*:delete`, на изменение — `*:edit`.

## 10. Тестируемость

**Тестов нет. Ни одного файла.** Поиск папок `test`, `tests`, `__tests__` — пусто. Ни фреймворка, ни фикстур, ни тестовой БД.

> **Если изменить важное бизнес-правило, поймают ли тесты регрессию?**
> Нет. Её найдёт пользователь в production. За два дня это уже происходило дважды: падение бота на `remove_keyboard` и повреждение `api.js` командой `sed`.

### Готовность кода к тестам

- **Легко тестируются:** `roles.js`, `channels.js`, `notifications.js` (включая `inQuietHours` с переходом через полночь), `ticket-types.js`, вспомогательные функции `import.js` (`parseDate`, `castValue`) и `api.js` (`hashPassword`, `verifyPassword`).
- **Средне:** `conversation.js` — чистая функция с сессией на входе, но нужна заглушка `db`.
- **Сложно:** обработчики роутов (SQL внутри), адаптеры мессенджеров.
- **Практически невозможно:** `index.html` без предварительного разделения.

### Критические сценарии без защиты

1. **Изоляция компаний** — аккаунт одной компании не видит данные другой. Ошибка здесь = утечка данных клиента.
2. **Права ролей** — сейчас они не работают в API; тест зафиксировал бы это сразу.
3. Вход, регистрация, блокировка при подборе, принятие приглашения.
4. Привязка водителя по всем четырём путям: идентификатор, ник, подтверждённый телефон, e-mail.
5. Маршрутизация уведомлений: заявка из MAX → ответ в MAX.
6. Тихие часы и отключение событий.
7. Эскалация: заявка старше порога повышается, свежая — нет.
8. Синхронизация связи водитель↔машина при назначении с обеих сторон.
9. Импорт: обновление по совпадению, пустая ячейка не затирает, отчёт по ошибочным строкам.
10. Идемпотентность `initSchema` — что повторный запуск не портит данные.

## 14. Масштабируемость

Текущая нагрузка: единицы компаний, единицы водителей, десятки заявок.

### При росте в 10 раз

Работать будет. Заметно:
- `/bootstrap` отдаёт до 400 заявок разом — сотни килобайт на загрузку страницы.
- Канбан перерисовывает DOM целиком при любом изменении, включая drag&drop.
- Один процесс держит HTTP, два бота и три таймера: всплеск сообщений притормозит API.

### При росте в 100 раз

Упрётся сразу в нескольких местах:

1. **Один экземпляр бота на токен.** Telegram не допускает два параллельных long polling — ошибка `409 Conflict` уже наблюдалась при пересечении контейнеров на деплое. Горизонтально не масштабируется без перехода на webhooks.
2. **Сессии ботов в памяти процесса** (`Map` в `conversation`/`max-bot`) — при нескольких репликах водитель будет терять контекст диалога.
3. **Счётчики попыток входа в памяти** — при репликах защита разъедется.
4. **Отсутствие транзакций** — гонки станут регулярными.
5. **`escalation.js` обновляет все заявки одним UPDATE** без ограничения — при десятках тысяч строк это долгая блокировка каждые 30 минут.
6. **Рассылка идёт в одном цикле с паузой 60 мс** — 1 000 водителей это минута синхронной работы внутри HTTP-запроса; запрос отвалится по таймауту.
7. **Пул соединений 10.**

**Архитектурный потолок — десятки компаний.** Не срочная проблема, но и не «на вырост навсегда».

## 16. Vendor / framework lock-in

### Нормальные зависимости

Четыре production-зависимости: `express`, `pg`, `telegraf`, `dotenv`. Для проекта такого размера это отлично — нечему протухать.

- **PostgreSQL** — стандартный SQL, из специфики только `JSONB` и `gen_random_uuid()`.
- **Express, Telegraf** — фактические стандарты, тонкий слой соприкосновения.
- **MAX Bot API** — реализован собственным HTTP-клиентом на `node:https` без SDK. Это плюс: нет зависимости от чужой библиотеки, полный контроль над сертификатами.
- **SheetJS (xlsx)** — подключается с CDN только в CRM, на сервер не влияет.

### Потенциально опасный lock-in

- **Railway** — умеренный. Сборка, переменные, домены, БД в одном месте. Переезд — день-два, но с ручным переносом данных. Отдельный вопрос — **бэкапы, привязанные к тарифу**.
- **CDN cdnjs для SheetJS** — если CDN недоступен, импорт молча перестанет работать. Мелочь, но незаметная в момент отказа.
- **Telegram и MAX** — продуктовое требование, не архитектурная ошибка.

**AI-сервисов, платных SaaS, проприетарных API нет.**

## 21. Финальный вывод

### 1. Это нормальный рабочий продукт или хрупкий vibe-coded прототип?

**Рабочий продукт, который развивается быстрее, чем укрепляется.**

За «продукт» говорит многое, и за двое суток этого стало больше. Логика диалога отделена от транспорта — второй мессенджер добавился адаптером, а не копипастом. Появились справочники каналов, ролей, событий. Заявка помнит канал происхождения. Подтверждение номера в MAX сделано криптографически корректно, хотя можно было схалтурить. Эскалация и автоперезапуск ботов отработали в бою. Это инженерные решения, а не набросок.

За «хрупкость» говорит то, что не изменилось: **ноль тестов**, **интерфейс диспетчера в одном файле на 3 872 строки**, **бэкапы не подтверждены**. И появилось новое: роли введены, но в основном API не применяются — механизм, который выглядит защитой, но ею не является.

Показательна статистика инцидентов: за два дня их было пять, три нашёл пользователь в production, ни один не был бы пойман тестами.

### 2. Можно ли безопасно наращивать функциональность?

**Да, но после нескольких обязательных исправлений.**

Архитектура выдержала проверку боем: за двое суток добавлены второй мессенджер, кабинет водителя, админка, импорт, роли, уведомления, рассылка, эскалация — и ничего не пришлось переписывать. Это лучшее доказательство, что фундамент рабочий.

Но темп изменений сейчас обгоняет надёжность. Перед следующим крупным блоком нужно закрыть пять пунктов: **бэкапы, экранирование, роли в API, CI-проверку, первые тесты**. Это 2–3 дня работы, которые окупятся на первом же инциденте.

Отдельно: перед добавлением девятого раздела в CRM стоит разделить `index.html` — иначе дальше будет только дороже.

### 3. Если автор исчезнет, сколько проблем будет у новой команды?

**Умеренные, с риском скатиться к серьёзным.**

Не «серьёзные» — код честный, модули понятные, комментарии объясняют неочевидное, а два аудита в репозитории заменяют архитектурную документацию. Senior разберётся за два-три дня.

Но объём вырос вдвое, интерфейсов теперь четыре, переменных окружения восемь, репозитория два — и всё это по-прежнему без README. Каждая неделя такого роста без документации сдвигает оценку в сторону «серьёзных».

Один день на README и три дня на тесты вернут ситуацию к «небольшим».

### 4. Главный риск прямо сейчас

**Отсутствие подтверждённых бэкапов базы данных.**

Ответ не изменился с прошлого аудита, и это само по себе тревожно. Все остальные риски — про стоимость разработки или про вероятный ущерб. Этот — про **необратимость**. XSS даёт захват аккаунта, но данные остаются. Отсутствие тестов ведёт к багам, но их чинят. Роли без проверок дают лишние удаления — восстановимо из бэкапа. Потеря базы означает исчезновение данных всех клиентов: компаний, водителей, машин, заявок, истории, аккаунтов. Восстанавливать будет неоткуда.

Стоимость закрытия — один час.
