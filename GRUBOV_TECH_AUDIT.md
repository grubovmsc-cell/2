**Дата:** 17 августа 2026
**Объект:** FleetDesk — CRM управления корпоративным автопарком + Telegram-бот для водителей
**Репозитории:** `grubovmsc-cell/2` (backend + бот), `grubovmsc-cell/fleetdesk-crm` (frontend)

## Как читать этот документ

Аудит написан для человека, который не писал этот код и, возможно, принимает проект.

Главный критерий оценки — не соответствие «идеальной архитектуре», а ответ на вопрос: **насколько дешево, безопасно и предсказуемо эту систему можно ремонтировать и развивать следующие 2–3 года.**

Оценки не смягчены. Но и придирок к работающему коду ради красоты здесь нет.

> **Важно про исходные данные.** `REPO_AUDIT.md` показывает «2 316 строк кода», но он не считает `.html` за код. Весь фронтенд — это один файл `index.html` примерно на 2 700 строк, и он в эту цифру не вошёл. Фактический объём системы — около **5 000 строк**, и больше половины из них живёт в одном файле. Это ключевой факт для всего дальнейшего разбора.

## 1. Карта системы

### Компоненты

| Слой | Что это | Где живёт |
|---|---|---|
| **Frontend (CRM)** | Одностраничное приложение на ванильном JS без сборки | `index.html` (репозиторий `fleetdesk-crm`), домен www.grubov.com |
| **Backend API** | Express-приложение, REST | `api.js`, смонтирован на `/api` в `bot-manager.js` |
| **Telegram-бот** | Telegraf, long polling, один бот на все компании | `bot.js`, запускается из `bot-manager.js` |
| **Процесс-хост** | Один Node-процесс: HTTP API + бот вместе | `bot-manager.js` |
| **База данных** | PostgreSQL (сервис Railway) | схема — `schema.js`, доступ — `db.js` |
| **Уведомления** | Отправка сообщений водителям в Telegram | `notifier.js` |
| **Справочник** | Типы заявок, общие для CRM и бота | `ticket-types.js` |

Внешних сервисов, кроме Telegram Bot API, нет. Очередей, кэша, файлового хранилища, брокеров сообщений — нет. Фоновые задачи — два `setInterval` внутри `api.js` (чистка счётчиков перебора и просроченных сессий).

### Поток данных: диспетчер

```
Диспетчер → браузер (index.html)
          → fetch с Bearer-токеном
          → Express /api/*  (api.js)
          → auth middleware: сессия → account → company_id
          → SQL напрямую из обработчика роута
          → PostgreSQL
          ↳ побочно: notifier.js → Telegram API → водитель
```

### Поток данных: водитель

```
Водитель → Telegram → long polling (Telegraf, bot.js)
        → middleware восстановления сессии: telegram_id / username → users
        → db.js → PostgreSQL
        ↳ заявка появляется в CRM при следующей загрузке /bootstrap
```

### Поток данных: обратная связь по заявке

```
Диспетчер пишет комментарий → PATCH /api/tickets/:id
   → api.js сравнивает старый и новый массив comments
   → notifier.notifyTicketComment → водителю сообщение с кнопкой «Ответить»
   → водитель отвечает в боте → db.addTicketComment
   → CRM подтягивает свежую заявку через GET /api/tickets/:id при открытии карточки
```

### Аутентификация и права

- **CRM:** e-mail + пароль (scrypt с солью), сессия — случайный 32-байтный токен в таблице `sessions`, хранится в `localStorage`, живёт 30 дней от последнего использования.
- **Бот:** пользователь опознаётся по `telegram_id`, при первом входе — по Telegram-нику из карточки водителя, в крайнем случае — по рабочему e-mail.
- **Роли:** **отсутствуют полностью.** В таблице `users` есть колонка `role` со значением по умолчанию `EMPLOYEE`, но она нигде не читается. Любой аккаунт компании имеет полный доступ ко всем данным своей компании.

### Изоляция компаний (multi-tenancy)

Каждый запрос к API проходит через `auth`, который кладёт `company_id` в `req.account`. Все SQL-запросы фильтруют по нему. Проверено: во всех обработчиках `api.js` условие `company_id = $N` присутствует. Утечек между компаниями не найдено.

### Deployment / эксплуатация

- Деплой: `git push` в GitHub → Railway собирает (nixpacks) и выкатывает автоматически.
- Конфигурация: `railway.toml` — старт `node bot-manager.js`, healthcheck `/health`, рестарт при падении (до 5 попыток).
- Секреты: переменные окружения Railway (`BOT_TOKEN`, `DATABASE_URL`, `NOTIFY_SECRET`).
- Миграции: `initSchema()` из `schema.js` выполняется при каждом старте, все операции идемпотентны (`IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`).
- CI/CD: **нет.** Ни тестов, ни линтера, ни проверок перед деплоем.
- Мониторинг: только логи Railway. Алертов нет.

## 2. Карта модулей

### `bot-manager.js` — композиционный корень (159 строк)

Единственная точка входа. Поднимает схему БД, запускает бота, монтирует API, настраивает CORS, держит эндпоинты `/notify`, `/bot-info`, `/health`.

Зависит от: `db`, `bot`, `schema`, `api`, `notifier`.
От него зависит: никто (это вершина графа).
**Автономность:** высокая. Роль ясная, размер небольшой. Заменяем целиком за час.

### `api.js` — REST API (597 строк) ⚠️ **самый крупный и нагруженный модуль**

Содержит: хеширование паролей, защиту от перебора, управление сессиями, middleware авторизации, весь CRUD (аккаунты, водители, ТС, подрядчики, заявки), нормализацию входных данных, `/bootstrap`.

Зависит от: `db`, `ticket-types`, `notifier`.
От него зависит: `bot-manager`.
**Автономность:** средняя. Внутри — четыре разные ответственности (auth, безопасность, валидация, доступ к данным), которые сейчас лежат вперемешку. SQL написан прямо в обработчиках роутов. Это **кандидат в God module**: пока не критично из-за небольшого размера, но растёт быстрее всех.

### `db.js` — доступ к данным (~180 строк)

Обёртка над `pg.Pool` плюс запросы, которые нужны боту (поиск пользователя, заявки, ТС, комментарии).

Особенность: используется **только ботом и notifier**. API работает с БД напрямую через `db.query`, минуя эти функции. То есть два разных стиля доступа к данным в одной системе.

**Автономность:** высокая, но роль размыта — это одновременно и инфраструктура (пул соединений), и репозиторий для бота.

### `bot.js` — Telegram-бот (~450 строк)

Диалоги: привязка аккаунта, создание заявки (тип → машина → описание), профиль водителя, ответ на комментарий диспетчера. Восстановление сессии из БД, общий перехватчик ошибок.

Зависит от: `db`, `ticket-types`.
От него зависит: `bot-manager`.
**Автономность:** высокая — бота можно переписать, не трогая CRM. Внутри — линейная цепочка `if` по `session.step`, читается нормально, но это ручной конечный автомат: каждый новый шаг диалога добавляет ветвление.

### `notifier.js` — исходящие уведомления (107 строк)

Три сценария: смена статуса, комментарий диспетчера, назначение подрядчика. Получает экземпляр бота через `setBot()`.

**Автономность:** высокая. Хороший модуль: единственная ответственность, чёткая граница, не знает про HTTP.

### `schema.js` — схема и миграции (203 строки)

Создание таблиц, идемпотентное добавление колонок, индексы, триггер `updated_at`.

**Автономность:** высокая. Но это не система миграций — см. раздел 6.

### `ticket-types.js` — справочник (23 строки)

Единый список типов заявок для бота и CRM. Маленький, правильный, снимает рассинхрон между системами.

### `index.html` — весь фронтенд (~2 700 строк) ⚠️ **God module**

Один файл содержит: CSS, разметку, состояние, работу с API, рендер всех экранов (канбан, автопарк, водители, подрядчики, бот), все модальные окна, все формы, авторизацию.

Рендер — строковые шаблоны, вставляемые через `innerHTML` (18 мест). Глобальные переменные `USERS`, `VEHICLES`, `CONTRACTORS`, `tickets`, `state` — общее изменяемое состояние на весь файл.

**Автономность:** нулевая — это и есть весь фронтенд. Разделить на части без сборщика можно только вручную.

### Классификация

| Тип | Модули |
|---|---|
| **Core** | `api.js`, `bot.js` |
| **Infrastructure** | `db.js`, `schema.js`, `bot-manager.js` |
| **Shared** | `ticket-types.js` |
| **Adapters / Integrations** | `notifier.js` (Telegram) |
| **God modules** | `index.html` (уже), `api.js` (становится им) |

## 3. Архитектура

### Что сделано хорошо

**Серверные модули разделены по-честному.** `notifier` не знает про HTTP, `bot` не знает про Express, `schema` не знает про бизнес-логику. Граф зависимостей — дерево, направленное к `bot-manager`. **Циклических зависимостей нет.**

**Единый справочник типов заявок** (`ticket-types.js`) — маленькое, но важное решение: раньше бот и CRM использовали разные идентификаторы типов, теперь рассинхрон невозможен по конструкции.

**Изоляция компаний реализована последовательно** — `company_id` протянут через все запросы, а не проверяется «где вспомнили».

**Уведомления вынесены на сервер.** Их шлёт API при изменении заявки, а не фронтенд. Значит, они сработают и при изменении из другого клиента.

### Что вызывает вопросы

**Доменного слоя нет.** Бизнес-правила живут в трёх местах одновременно:
- в обработчиках роутов (`api.js`) — что считать сменой статуса, кого уведомлять;
- в диалогах бота (`bot.js`) — как создаётся заявка, какой номер ей присвоить;
- в браузере (`index.html`) — фильтрация, подсчёт статусов, отображение приоритетов.

Пример дублирования: генерация номера заявки написана дважды — `nextTicketNum()` в `api.js` и `getNextTicketNum()` в `db.js`. Логика одинаковая, форматы совпадают, но это две независимые копии.

**Бизнес-логика внутри UI.** Фильтрация заявок, подсчёт просроченных документов, определение «активных» заявок, вычисление предупреждений по ВУ и медсправке — всё это в `index.html`. Мобильное приложение или второй клиент придётся писать с нуля вместе с правилами.

**Глобальное изменяемое состояние на фронте.** `USERS`, `VEHICLES`, `tickets`, `state` — модули переопределяют их из разных функций. Отследить, кто и когда поменял данные, можно только чтением всего файла.

**Прямой SQL в роутах.** В `api.js` запросы написаны в обработчиках. При смене СУБД или добавлении кэша придётся править каждый обработчик.

**Dependency inversion отсутствует** — но для системы такого размера это скорее нормально, чем плохо. Абстракции ради абстракций здесь были бы вредны.

### Скрытые зависимости

1. **`notifier.setBot()`** — если забыть вызвать, уведомления молча перестанут работать. Ошибки не будет, просто тишина.
2. **Формат `comments`/`history` в JSONB** — структура объектов (`author`, `text`, `time`, `internal`, `fromDriver`) не описана нигде и поддерживается соглашением между `api.js`, `bot.js` и `index.html`. Изменение поля в одном месте тихо ломает два других.
3. **`DEFAULT_API` в `index.html`** — адрес сервера прошит в коде фронтенда. При смене домена бэкенда нужно не забыть про него.

## 4. Ремонтопригодность

Сценарий: пользователь пишет «перестало работать».

| Этап | Оценка | Комментарий |
|---|---|---|
| Найти место ошибки | **Средне** | На бэкенде — быстро: логи с префиксами `[api]`, `[bot]`, `[notifier]`, ошибки пишутся с контекстом. На фронте — тяжело: один файл, ошибки в консоли браузера, которых никто не видит |
| Воспроизвести | **Тяжело** | Нет staging-окружения. Локальный запуск требует своей БД и своего бота — инструкции нет |
| Понять контекст | **Средне** | Код читаемый, комментарии осмысленные и по делу. Но нет README и описания бизнес-процессов |
| Исправить | **Легко** | Модули небольшие, зависимости прозрачные |
| Убедиться, что не сломал соседнее | **Очень тяжело** | **Тестов нет ни одного.** Проверка — только ручная |
| Выкатить | **Легко** | `git push` → Railway. Быстро |

### Наблюдаемость

**Есть:** структурированные префиксы в логах, healthcheck `/health` с состоянием бота, `bot.catch()` в Telegraf, авто-перезапуск polling, политика рестарта в `railway.toml`.

**Нет:** идентификаторов запросов (невозможно связать цепочку логов), уровней логирования, алертов, метрик, истории изменений сущностей (кто и когда правил карточку водителя), staging-окружения.

### Где баг будет сложно локализовать

1. **Уведомления не дошли.** Причин пять: бот не запущен, у водителя нет `telegram_id`, он не нажимал `/start`, `notifier.setBot()` не вызван, Telegram вернул ошибку. В логах будет либо `[notifier] send error`, либо вообще ничего — функция молча возвращает `0`, если не нашла получателя.
2. **Данные в CRM «не те».** Слоя между API и рендером почти нет, преобразование идёт в `fromServerTicket` / `fromServerDriver`. Если поле потерялось — искать придётся по всей цепочке от SQL до шаблона.
3. **Бот «залип» в диалоге.** Состояние в памяти процесса. После рестарта Railway сессия обнуляется. Восстановление пользователя сделано, но `session.step` теряется — водитель может оказаться в неожиданном месте диалога.

## 5. Изменяемость: мысленные тесты

### A. Добавить новое поле к заявке

**Менять:** `schema.js` (колонка), `api.js` (2 места: INSERT и UPDATE), `index.html` (форма + рендер), возможно `notifier.js`.
**Уровней:** 3. **Риск:** низкий. **Локализовано:** удовлетворительно.
Поля собраны в списках (`DRIVER_FIELDS`, `VEHICLE_FIELDS`, `CONTRACTOR_FIELDS`) — это удачное решение, добавление поля к водителю или ТС дешевле, чем к заявке, где SQL написан вручную.

### B. Добавить роль пользователя с отдельными правами

**Менять:** схему, `auth`, **каждый эндпоинт** в `api.js`, навигацию и рендер в `index.html`.
**Уровней:** 4. **Риск:** высокий. **Локализовано:** плохо.
Сейчас нет ни одной точки, где проверяются права — их придётся создать с нуля и не забыть ни один из ~20 эндпоинтов. **Это самое дорогое изменение из списка.**

### C. Добавить новый статус заявки

**Менять:** `notifier.STATUS_LABELS`, `bot.js` (иконки статусов), `index.html` (колонки канбана, кнопки статусов, фильтры, подписи — 5+ мест).
**Уровней:** 3. **Риск:** средний. **Дублирование:** да — списки статусов продублированы в трёх файлах, каждый со своими подписями.

### D. Добавить внешнюю интеграцию (например, SMS)

**Менять:** новый модуль по образцу `notifier.js`, точки вызова в `api.js`.
**Уровней:** 2. **Риск:** низкий. **Локализовано:** хорошо.
`notifier.js` — удачный образец для копирования. Это самое дешёвое изменение.

### E. Изменить ключевое бизнес-правило (например, кого уведомлять)

**Менять:** `notifier.js` и условия в `api.js`.
**Риск:** средний — **проверить нечем**, регрессию поймает только пользователь.

### F. Добавить новый экран

**Менять:** `index.html` — `setPage()`, новая функция рендера, пункт меню, `refreshCurrentPage()`.
**Уровней:** 1. **Риск:** средний — файл растёт, каждый новый экран увеличивает вероятность конфликтов и опечаток в общем состоянии.

### G. Заменить базу данных

**Менять:** `db.js` (можно) + **каждый обработчик `api.js`** (SQL написан в них).
**Риск:** очень высокий. Фактически это переписывание слоя доступа к данным.

### H. Заменить Telegram на другой мессенджер

**Менять:** `bot.js`, `notifier.js`, привязку пользователей в схеме.
**Риск:** высокий, но это осознанная зависимость от продуктового требования, а не архитектурная ошибка.

**Вывод:** система хорошо принимает изменения «вширь» (новые поля, интеграции, экраны) и плохо — «вглубь» (права доступа, смена хранилища, изменение статусной модели).

## 6. База данных

### Модель

7 таблиц: `companies`, `accounts`, `sessions`, `users`, `vehicles`, `contractors`, `tickets`. Модель простая и адекватная предметной области. Нормализация разумная, переусложнения нет.

### Что сделано правильно

- Внешние ключи расставлены везде, с осмысленными `ON DELETE`: удаление компании уносит все её данные (`CASCADE`), удаление водителя не ломает заявки (`SET NULL`).
- Индексы покрывают реальные запросы: `company_id`, `telegram_id`, `LOWER(telegram_username)`, `LOWER(email)`, `status`, `contractor_id`, составной `(company_id, created_at DESC)`.
- `updated_at` обновляется триггером, а не забывчивым разработчиком.
- Уникальный индекс на `LOWER(email)` в `accounts` — регистронезависимая почта сделана правильно.

### Проблемы

**1. Миграции необратимы и не версионированы.** `schema.js` умеет только добавлять. Откатить изменение нельзя, узнать «какая версия схемы на проде» — тоже. Пока таблиц семь, это терпимо. При двух разработчиках и параллельных ветках начнутся расхождения.

**2. Транзакций нет ни одной.** Наиболее заметно в `PATCH /tickets/:id`: чтение текущей заявки и запись новой — два отдельных запроса. Если два диспетчера одновременно добавят комментарий, один потеряется (классическая гонка «прочитал–изменил–записал»). При нынешней нагрузке маловероятно, но это реальный дефект, а не теоретический.

**3. `comments` и `history` в JSONB.** Решение удобное и для текущих объёмов правильное. Минусы: нельзя искать по комментариям средствами БД, нельзя добавить внешний ключ на автора, структура объекта нигде не описана и держится на договорённости трёх файлов.

**4. Статусы — свободный текст.** `status`, `priority`, `type_key` — обычные `TEXT` без `CHECK`. Опечатка в коде создаст заявку со статусом, который не отобразится ни в одной колонке канбана, и БД это молча примет.

**5. `tickets` — центральная таблица.** Ссылается на компанию, ТС, двух пользователей и подрядчика. Это естественно для предметной области, но любое изменение её структуры затрагивает и бота, и CRM, и уведомления.

**6. Мягкого удаления нет.** Удаление водителя, ТС или подрядчика — физическое. Заявки выживают (`SET NULL`), но история «кто это был» теряется безвозвратно.

**7. Двусмысленные поля.** В `users` одновременно `tachograph` (текст — серийный номер) и `has_tachograph` (логическое). Ещё: связь водителя и машины хранится с двух сторон — `users.assigned_vehicle` и `vehicles.assigned_user_id`. Синхронизация между ними не гарантирована; `db.getAssignedVehicle()` вынужден проверять оба поля. Это источник будущих расхождений.

**8. N+1 запросов** в списочных операциях нет — `/bootstrap` делает 5 запросов на всю страницу. Здесь всё хорошо.

## 7. API

### Структура

REST под `/api`, ресурсы во множественном числе (`/drivers`, `/vehicles`, `/tickets`, `/contractors`), корректные глаголы (GET/POST/PATCH/DELETE), плюс `/auth/*` и агрегирующий `/bootstrap`. Именование единообразное, читается предсказуемо.

### Что хорошо

- Все запросы параметризованные — **SQL-инъекций нет**. Динамическая сборка `SET` идёт по фиксированным белым спискам полей, пользовательские данные в имена колонок не попадают.
- `/bootstrap` — грамотное решение: одна загрузка вместо пяти запросов с фронта.
- Ошибки возвращаются в едином формате `{ error: "текст" }`, сообщения на русском и понятны конечному пользователю.
- Пагинация в `/bootstrap` есть (последние 400 заявок, лимит настраивается).

### Что плохо

**1. Валидации входных данных практически нет.** Проверяется только наличие обязательных полей. Не проверяются: формат e-mail, длина строк, диапазоны чисел, корректность дат, принадлежность `vehicleId` к той же компании. Последнее — реальная дыра: можно привязать к своей заявке чужой автомобиль, передав его идентификатор (правда, узнать чужой UUID неоткуда, поэтому эксплуатация маловероятна).

**2. Внутренняя модель БД торчит наружу.** Ответы — это `rows[0]`, то есть строки таблиц как есть. DTO нет. Переименование колонки немедленно ломает фронтенд. Частично сглажено функциями `fromServerTicket` / `fromServerDriver` на фронте, но это заплатка, а не контракт.

**3. Версионирования нет.** `/api/v1/` отсутствует. Пока клиент один и деплоится вместе с бэкендом — не проблема. Появится мобильное приложение — станет проблемой сразу.

**4. Идемпотентности нет.** Повторный POST создаст дубль. Для CRM с ручным вводом терпимо.

**5. Сообщения об ошибках отдают внутренности.** В нескольких местах наружу уходит `err.message` из PostgreSQL — например, `res.status(500).json({ error: err.message })`. Это подсказывает атакующему структуру БД. Severity: Low, но чинится в одну строку.

### Ответ на ключевой вопрос

> Можно ли изменить внутреннюю модель, не сломав фронтенд?

**Нет.** Между таблицами и клиентом нет слоя преобразования. Переименование колонки в БД сломает CRM в тот же момент. Пока фронтенд один и выкатывается синхронно — цена ошибки невысока.

## 8. Frontend

Это самая слабая часть системы.

### Факты

- Один файл `index.html`, ~2 700 строк: стили, разметка, состояние, сеть, рендер, модальные окна.
- Ни сборщика, ни модулей, ни фреймворка. Файл заливается в GitHub через веб-интерфейс и раздаётся статикой.
- Рендер — строковая склейка HTML и `innerHTML` (18 мест).
- Состояние — глобальные переменные `USERS`, `VEHICLES`, `CONTRACTORS`, `tickets`, `state`.

### Что работает хорошо

Отсутствие сборки — осознанный и в чём-то удачный выбор для этого этапа: нет node_modules, нет конфигов, файл открывается и правится где угодно. Обработка ошибок сети единообразна (`api()` централизует запросы, 401 приводит к выходу). Индикаторы загрузки и всплывающие уведомления есть.

### Что создаёт риск

**1. XSS через `innerHTML`.** Данные вставляются в разметку без экранирования: имена водителей, названия подрядчиков, заголовки и описания заявок, **тексты комментариев**. Подробнее — в разделе 9, там это главный риск безопасности.

**2. Изменение общих функций ломает несколько экранов.** `renderFleetPage()` вызывается из мест, связанных с автопарком, водителями и подрядчиками. `refreshCurrentPage()` завязана на `state.page`. `saveVModal()` — одна функция на три разных типа карточек, разветвлённая по `vModalContext.type`. Ошибка в любой из них проявится в нескольких разделах сразу.

**3. Формы без валидации.** Проверяется только заполненность отдельных полей. Даты, телефоны, числа принимаются как есть и уходят на сервер, где тоже не проверяются.

**4. Дублирование справочников.** `TICKET_TYPES`, названия статусов, подписи приоритетов существуют и на сервере, и в `index.html` — отдельными копиями.

**5. Доступность (accessibility) не рассматривалась.** Нет `aria`-атрибутов, модальные окна не удерживают фокус, навигация с клавиатуры ограничена. Для внутреннего инструмента это приемлемо.

## 9. Авторизация и безопасность

### Риски по severity

| # | Риск | Severity | Где | Детали |
|---|---|---|---|---|
| 1 | **XSS через комментарии водителя** | **Critical** | `index.html`, рендер комментариев | Водитель отправляет через бота текст с HTML-разметкой → он сохраняется в `tickets.comments` → диспетчер открывает карточку → `innerHTML` исполняет вставленный скрипт в браузере диспетчера. Токен сессии лежит в `localStorage` и доступен скрипту. Это полный захват аккаунта диспетчера человеком, у которого есть только Telegram |
| 2 | **XSS через поля карточек** | **High** | `index.html`, все рендеры | Тот же механизм для имён, названий, описаний. Требует доступа к CRM, поэтому опаснее в сценарии «обиженный сотрудник» |
| 3 | **Нет ролей и прав** | **High** | `api.js` целиком | Любой аккаунт компании может всё: удалять водителей, править чужие заявки, стирать подрядчиков. Разделения «диспетчер / механик / руководитель» не существует |
| 4 | **Нет валидации входных данных** | **Medium** | `api.js` | Длина строк, форматы, диапазоны не проверяются. Можно записать мегабайтный текст в поле имени |
| 5 | **Внутренние ошибки БД наружу** | **Low** | `api.js`, обработчики `catch` | `err.message` из PostgreSQL уходит клиенту |
| 6 | **Нет требований к паролю** | **Low** | `api.js`, `/auth/register` | Минимум 6 символов, «123456» подойдёт |
| 7 | **Токены в `localStorage`** | **Medium** | `index.html` | Доступны любому скрипту на странице. В связке с риском №1 это и даёт критичность |
| 8 | **Секреты попадали в скриншоты** | **Medium** | процесс, не код | GitHub-токены вводились в терминал и дважды оказывались на снимках экрана. Оба отозваны, но процесс деплоя провоцирует повторение |

### Что закрыто хорошо

- **Пароли** — `scrypt` со случайной 16-байтной солью, сравнение через `timingSafeEqual`. Сделано правильно, без самодеятельности.
- **SQL-инъекции** — исключены параметризацией.
- **Изоляция компаний** — последовательная, проверена по всем эндпоинтам.
- **CORS** — ограничен списком доменов, есть `Vary: Origin`.
- **Перебор паролей** — 8 попыток по IP и e-mail, блокировка на 15 минут.
- **Сессии** — 30 дней от последнего использования, просроченные удаляются.
- **Секретов в репозитории нет** — в `.env.example` только шаблоны.
- **CSRF неактуален** — авторизация через заголовок `Authorization`, а не cookie, межсайтовый запрос токен не подставит.

### Главная рекомендация по безопасности

Одна функция экранирования и её применение ко всем подстановкам в `innerHTML` закрывает риски №1 и №2. Это работа на 1–2 часа и она **важнее всех остальных пунктов этого аудита**.

## 10. Тестируемость

**Тестов в проекте нет. Ноль файлов.**

Не «мало покрытия» — инструментов тестирования нет вообще: ни фреймворка, ни фикстур, ни тестовой БД, ни моков.

> **Если изменить важное бизнес-правило, поймают ли тесты регрессию?**
> Нет. Регрессию обнаружит пользователь в production.

### Насколько код готов к тестированию

- `notifier.js`, `ticket-types.js`, вспомогательные функции `api.js` (`hashPassword`, `verifyPassword`, `nz`, `int`, `driverValues`) — тестируются легко, они чистые.
- Обработчики роутов — сложнее: SQL внутри, нужна тестовая БД или моки `db.query`.
- Диалоги бота — сложно: состояние в сессии, зависимость от Telegraf.
- Фронтенд — практически невозможно без предварительного разделения файла.

### Критические сценарии без защиты

1. Регистрация и вход, включая блокировку при переборе.
2. **Изоляция компаний** — что аккаунт одной компании не видит данные другой. Ошибка здесь = утечка данных клиента.
3. Создание заявки из бота с корректным номером.
4. Отправка уведомлений при смене статуса, комментарии, назначении подрядчика.
5. Опознание водителя по Telegram-нику и восстановление сессии после рестарта.
6. Идемпотентность миграций — что `initSchema()` не портит данные при повторном запуске.

## 12. Git и точки нестабильности

По данным `REPO_AUDIT.md` за всю историю (~30 коммитов):

| Файл | Изменений | Размер | Тесты | Оценка |
|---|---:|---:|---|---|
| `bot.js` | 7 | 450 строк | нет | ⚠️ **горячая зона** |
| `db.js` | 5 | 180 строк | нет | ⚠️ горячая зона |
| `bot-manager.js` | 5 | 159 строк | нет | умеренно |
| `api.js` | 4 | 597 строк | нет | ⚠️ **горячая зона** |
| `notifier.js` | 3 | 107 строк | нет | умеренно |
| `index.html` | 1 | 2 700 строк | нет | ⚠️ статистика обманчива |

**Важная оговорка:** `index.html` показывает одно изменение только потому, что живёт в другом репозитории и заливается через веб-интерфейс GitHub. Фактически он менялся чаще всех остальных файлов. Git-история фронтенда фрагментирована — это отдельная проблема.

**Самые опасные зоны** (сложный код + частые изменения + нулевое покрытие тестами):

1. **`bot.js`** — больше всего правок, конечный автомат на `if`, состояние в памяти. За последние дни здесь было два падения production: `remove_keyboard` в `editMessageText` и блокирующий `await bot.launch()`. Оба обнаружены пользователями, не тестами.
2. **`api.js`** — самый большой серверный файл, растёт быстрее всех, содержит и авторизацию, и бизнес-логику.
3. **`index.html`** — размер и реальная частота изменений максимальны.

**Исторический факт, показательный для оценки процесса:** ручное удаление кода через `sed` по номерам строк повредило `api.js` — вырезало часть работающего эндпоинта. Обнаружено при аудите, до деплоя. Без тестов и без CI такие поломки доходят до production.

## 13. Зависимость от автора

### Что помогает новому разработчику

- Стек предельно мейнстримный: Node, Express, PostgreSQL, Telegraf. Никакой экзотики.
- Код читается: осмысленные имена, комментарии на русском объясняют **почему**, а не **что** — например, комментарий про `bot.launch()`, который не резолвится в Telegraf 4, экономит новому человеку полдня отладки.
- Модулей мало, роли понятны из имён файлов.
- Схема БД собрана в одном месте и самодокументируема.

### Что мешает

- **README нет.** Как запустить локально, какие переменные окружения нужны, где какой репозиторий, как связаны три сервиса Railway — нигде не написано. Единственный документ, `deploy/DEPLOY.md`, описывает **устаревший** сценарий с Yandex Cloud, которым больше не пользуются. Это хуже отсутствия документации: она активно вводит в заблуждение.
- **Два репозитория без перекрёстных ссылок.** Что фронтенд лежит отдельно и заливается вручную — знание, существующее только в голове.
- **Ручной деплой фронтенда** через веб-интерфейс GitHub — процесс нигде не зафиксирован.
- **Нет описания бизнес-процессов.** Что означают статусы, кто кого уведомляет, зачем нужен `fromDriver` в комментариях — восстанавливается только чтением кода.
- **Локальный запуск не описан** и, судя по всему, не проверялся: нужен свой Postgres и отдельный тестовый бот, иначе два процесса подерутся за long polling.

### Bus Factor: **4 из 10**

Senior-разработчик поднимет проект и разберётся в архитектуре за 1–2 дня — код небольшой и честный. Но первые недели он будет работать вслепую: без тестов, без staging, без документации, правя production напрямую. Знания о процессах (два репозитория, ручная заливка фронта, ввод токена в `push.sh`) придётся восстанавливать методом проб.

Оценка «4», а не ниже, потому что кодовая база маленькая и понятная. Не выше — потому что вся эксплуатация держится на неписаных договорённостях.

## 14. Масштабируемость

Текущая нагрузка: единицы компаний, десятки водителей, сотни заявок. Для неё система избыточно надёжна.

### При росте в 10 раз (десятки компаний, сотни водителей)

Работать будет. Заметные шероховатости:

- `/bootstrap` начнёт отдавать сотни килобайт на каждую загрузку страницы.
- Отрисовка канбана перестраивает DOM целиком при любом изменении — станет заметно подтормаживать.
- Один Node-процесс держит и HTTP, и бота: всплеск сообщений в Telegram притормозит API.

### При росте в 100 раз (сотни компаний, тысячи водителей)

Упрётся в несколько мест сразу:

1. **Один экземпляр бота.** Telegram не допускает два параллельных long polling с одним токеном — это уже наблюдалось как ошибка `409: Conflict` при пересечении контейнеров на деплое. Горизонтально не масштабируется, нужен переход на webhooks.
2. **Счётчик перебора паролей в памяти процесса** — при нескольких репликах защита разъедется.
3. **Сессии бота в памяти** — при нескольких репликах водитель будет терять контекст диалога.
4. **`/bootstrap` без реальной пагинации на фронте** — интерфейс держит все заявки в памяти браузера.
5. **Отсутствие транзакций** — гонки при одновременной работе станут регулярными, а не теоретическими.
6. **Пул соединений 10** — упрётся раньше остального.

**Вывод:** архитектурный потолок — примерно десятки компаний. Это не срочная проблема, но и не «на вырост навсегда».

## 15. Deployment и эксплуатация

### Что есть

- Автоматическая сборка и выкатка при push (Railway + nixpacks).
- `healthcheckPath = /health`, отдающий реальное состояние бота.
- `restartPolicyType = on_failure` до 5 попыток.
- Авто-перезапуск polling бота при обрыве — уже спас систему при конфликте контейнеров.
- Миграции применяются автоматически при старте, идемпотентно.
- Секреты в переменных окружения Railway, не в коде.

### Чего нет

- **CI/CD-проверок.** Ни линтера, ни `node --check`, ни тестов перед деплоем. В main попадает всё.
- **Staging-окружения.** Проверка идёт на production.
- **Отката.** Только «откатить коммит и задеплоить заново».
- **Резервных копий БД.** Не настроены и не проверялись — при текущем тарифе Railway это надо явно уточнить. **Восстановление не репетировалось ни разу.**
- **Алертов.** Падение обнаруживается тем, что пользователь пишет «бот не отвечает» — так и происходило.
- **Централизованных логов.** Только веб-консоль Railway, история ограничена.

### Ответ на вопрос

> Если production упадёт ночью, насколько понятно, что произошло и как восстановить?

**Что произошло — умеренно понятно.** Логи с префиксами есть, `/health` показывает состояние бота, Railway хранит статусы деплоев. Но узнаете вы об этом только утром от пользователей.

**Как восстановить — понятно для сбоев кода** (откатить коммит, передеплоить). **Непонятно для потери данных:** бэкапов нет, процедура восстановления не описана и не проверялась. Потеря базы сегодня означает потерю всех данных клиентов.

## 16. Vendor / framework lock-in

### Нормальные зависимости

- **PostgreSQL** — используется стандартный SQL, специфичных возможностей минимум (`JSONB`, `gen_random_uuid()`). Миграция на другую СУБД трудоёмка из-за SQL в роутах, а не из-за самой БД.
- **Express** — фактический стандарт, маленькая площадь соприкосновения.
- **Telegraf** — тонкая обёртка над Telegram API, заменяем.
- **`pg`, `dotenv`** — базовые библиотеки, риска нет.

Зависимостей всего четыре в production. Для проекта такого возраста это очень хорошо: нечему протухать, нечему ломаться при обновлении.

### Потенциально опасный lock-in

- **Railway** — умеренный. Сборка через nixpacks, переменные окружения, домены, БД — всё в одном месте. Переезд на другой хостинг займёт день-два, но потребует ручного переноса данных и перенастройки. Отдельный вопрос — **бэкапы БД, привязанные к тарифу**.
- **Telegram** — жёсткая зависимость, но это продуктовое требование, а не архитектурная ошибка. Отмечать как риск некорректно.

**AI-сервисов, платных SaaS, проприетарных API в проекте нет.**

**Modularity — 4.** На сервере модульность приличная: `notifier`, `schema`, `ticket-types` изолированы и заменяемы. Оценку роняет фронтенд — 2 700 строк без единой границы — и `api.js`, вобравший авторизацию, безопасность, валидацию и доступ к данным.

**Security architecture — 4.** База сделана правильно: scrypt с солью, параметризованные запросы, изоляция компаний, CORS по списку, защита от перебора, срок жизни сессий. Но XSS через `innerHTML` в связке с токеном в `localStorage` даёт критичный вектор, а ролей нет вовсе.

**Developer onboarding — 5.** Стек мейнстримный, код небольшой и понятный, комментарии по делу. Но README нет, единственный документ описывает устаревший сценарий деплоя, локальный запуск не описан, а про второй репозиторий надо просто знать.

**Bus factor — 4.** Новый senior разберётся за пару дней, но первые недели будет работать без страховки: правки сразу в production, без тестов и без документации по процессам.

**C1. SQL внутри роутов.** Выглядит «неправильно», но при семи таблицах и одном клиенте репозиторный слой добавит уровень абстракции без реальной выгоды. Возвращаться к этому — когда появится второй клиент или вторая СУБД.

**C3. `comments` и `history` в JSONB.** Для нынешних объёмов это удобно и быстро. Раскладывать в отдельные таблицы — когда понадобится поиск по комментариям или права на уровне записи.

**C4. Long polling у бота.** До десятков компаний работает надёжно, а с авто-перезапуском ещё и самовосстанавливается. Webhooks — при реальном росте, не раньше.

**C5. Единый процесс для API и бота.** Разделение на два сервиса добавит операционной сложности без выигрыша на текущих объёмах.

## 21. Финальный вывод

### 1. Это нормальный рабочий продукт или хрупкий vibe-coded прототип?

**Это рабочий продукт, выросший из прототипа, и след прототипа ещё виден.**

За «продукт» говорит серверная часть: разделённые модули, честная изоляция компаний, параметризованные запросы, корректная работа с паролями, самовосстановление бота, автодеплой с healthcheck. Это не набросок — это код, который писали с пониманием, что он будет работать. Комментарии, объясняющие неочевидные решения (вроде поведения `bot.launch()` в Telegraf 4), — признак инженерной, а не одноразовой работы.

За «прототип» говорят три вещи: **ноль тестов**, **фронтенд одним файлом на 2 700 строк** и **отсутствие резервных копий**. Плюс процессы, живущие в голове автора: два репозитория, ручная заливка фронтенда, деплой с вводом токена в терминал.

Система работает и приносит пользу. Но её надёжность сегодня держится на аккуратности одного человека, а не на устройстве проекта.

### 2. Можно ли безопасно наращивать функциональность на существующей архитектуре?

**Да, но после нескольких обязательных исправлений.**

Архитектура позволяет добавлять функции — модули разделены, зависимости не запутаны, новая интеграция или новое поле делаются за часы. Ограничений, требующих переписывания, нет.

Но перед следующей крупной функцией нужно закрыть четыре пункта: **бэкапы**, **экранирование HTML**, **проверка синтаксиса в CI**, **тесты на критичные сценарии**. Без них каждая новая функция увеличивает вероятность тихой поломки старой, а обнаруживать её будут клиенты. Это 3–4 дня работы, которые окупятся на первом же инциденте.

Отдельно: перед добавлением ролей или существенным усложнением интерфейса стоит разделить `index.html`. Иначе дальше будет только дороже.

### 3. Если автор исчезнет, сколько проблем будет у новой команды?

**Умеренные.**

Не «серьёзные» — потому что кодовая база маленькая, стек стандартный, код читается, а комментарии написаны для человека. Senior разберётся в архитектуре за один-два дня.

Не «небольшие» — потому что первые недели новая команда будет работать вслепую: без тестов, без staging, без описания процессов. Она не будет знать, что фронтенд в другом репозитории и заливается вручную, что `deploy/DEPLOY.md` описывает неиспользуемый сценарий, что локальный запуск бота требует отдельного тестового токена. Каждое из этих открытий — потерянные полдня.

Один день на написание README и три дня на тесты снижают эту оценку до «небольших».

### 4. Главный риск прямо сейчас

**Отсутствие резервных копий базы данных.**

Все остальные риски — про стоимость разработки или про вероятный ущерб. Этот — про **необратимость**. XSS даёт захват аккаунта, но данные остаются. Отсутствие тестов ведёт к багам, но их чинят. Потеря базы Railway означает, что данные всех клиентов исчезают навсегда: заявки, водители, история, аккаунты. Восстанавливать будет неоткуда, и это конец продукта, а не инцидент.

Стоимость закрытия — один час. Соотношение цены и последствий здесь несопоставимо ни с чем другим в этом отчёте.

### 5. Первые пять действий на месте CTO

1. **Включить бэкапы БД и провести пробное восстановление.** Сегодня. Пока это не сделано, всё остальное — обсуждение деталей на фоне возможной полной потери данных.
2. **Добавить CI-проверку синтаксиса на push.** Тридцать минут. Прецедент, когда сломанный файл едва не уехал в production, уже был.
3. **Закрыть XSS экранированием HTML.** Один-два часа. Единственная дыра, через которую посторонний человек может получить доступ к чужим данным.
4. **Написать 10–15 тестов на критичные сценарии** — вход, изоляция компаний, создание заявки, уведомления. Один день. Это превращает «страшно менять» в «можно менять».
5. **Написать README и удалить устаревшую документацию.** Два часа. Снимает главный барьер для второго разработчика и заодно фиксирует знания, которые сейчас существуют в единственном экземпляре.

Ничего из этого не требует переписывания кода. Пять действий, около четырёх рабочих дней — и проект перестаёт быть уязвимым к единичной ошибке или уходу одного человека.
